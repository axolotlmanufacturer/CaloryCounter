## 1. Your role and the goal

You are a senior Android engineer. Build a complete, production-quality, **fully offline** Android app with a **German** user interface that:

1. logs food intake (kcal + Eiweiß / Kohlenhydrate / Fett) per day and meal,
2. calculates BMR (Grundumsatz), TDEE (Gesamtumsatz) and a safe daily calorie target for a weight goal (Kaloriendefizit / -überschuss),
3. finds foods in a bundled offline database (BLS + Open Food Facts Germany) and via an offline barcode scanner,
4. tracks body weight with a trend line and progress charts,
5. ships as a signed release `.apk`.

Work in the phases from section 12. **Stop after each phase, report, and wait for my "weiter" before continuing.** Begin in plan mode: read this entire file, then propose your plan for Phase 0 and 1 before writing any code.

## 2. Hard requirements (non-negotiable)

1. **Offline by design.** The final merged manifest must NOT contain `android.permission.INTERNET`. No analytics, crash reporting, ads, Firebase or Google Play Services dependencies. Add `<uses-permission android:name="android.permission.INTERNET" tools:node="remove"/>` as a safeguard and verify on the release APK (`apkanalyzer manifest permissions` or `aapt2 dump permissions`).
2. **Never invent nutrition values.** Every nutrient number comes from BLS, Open Food Facts (via the build pipeline) or user input. Missing values are shown as "–", never guessed. Typical portion weights may be estimated, but must be flagged `estimated = true` and listed for my review.
3. **German UI.** All user-facing text lives in `res/values/strings.xml` (German is the default locale); no hardcoded strings in Composables. German formatting everywhere: `1.234 kcal`, `72,4 kg`, `13.10.2026`. Weeks start on Monday. Metric units only.
4. **Only one permission: `CAMERA`**, requested in context when the scanner opens, with a rationale. The app must be fully usable if it is denied. Declare `<uses-feature android:name="android.hardware.camera" android:required="false"/>`.
5. **Privacy.** All data stays on the device. Configure `dataExtractionRules` / `fullBackupContent` to exclude everything from cloud backup but allow device-to-device transfer.
6. The **health safety rules in §6.4** must be implemented exactly and unit-tested.
7. At the end of every phase: `./gradlew lint test` passes.

## 5. Data

### 5.1 Food database `foods.db` (read-only, shipped as an asset)

| Source | Purpose |
|---|---|
| **BLS 4.0** – Bundeslebensmittelschlüssel, Max Rubner-Institut (blsdb.de) | ~7,100 generic foods with German names ("Apfel, roh", "Vollkornbrot") |
| **Open Food Facts** – Germany subset | Branded packaged products with barcodes (no product images, to keep the APK small) |

This app is for private use only and will not be published, so no license notices or attribution screens are needed.

**Builder pipeline** (`tools/food-db-builder/build_food_db.py`):

1. **Inputs.** BLS file in `data/raw/bls/` (if the download needs registration, tell me and I will download it manually). Open Food Facts export: prefer the Parquet export queried with DuckDB (select only needed columns), otherwise the CSV export (it is tab-separated). Check the current URLs and formats at openfoodfacts.org/data. **Before downloading anything larger than 500 MB, tell me the size and ask.**
2. **BLS mapping.** Map energy (kcal), protein, available carbohydrates, sugar, fat, fiber, salt (sodium × 2.5 if only sodium is given). Document the column mapping in the README.
3. **OFF filters** (verify actual field names):
   - `countries_tags` contains `en:germany`
   - valid barcode: 8, 12, 13 or 14 digits with a correct check digit
   - name: `product_name_de`, fallback `product_name`; drop rows without a name
   - kcal from `energy-kcal_100g`, else `energy-kj_100g / 4.184`; drop rows without energy
   - sanity: 0 ≤ kcal ≤ 900; each macro 0–100 g; protein + carbs + fat ≤ 105 g
   - plausibility vs. 4/4/9 kcal per g (allow leeway for alcohol, fiber, polyols): only drop egregious mismatches
   - dedupe by normalized barcode, keep the most recently modified row
   - mark liquids (quantity in ml/l) with `per_unit = 'ml'`
4. **Report** rows in/out per filter step, final counts per source, and DB size.
5. **Schema sync.** Create tables using the exact `createSql` statements from Room's exported schema JSON so `createFromAsset` validation passes. Set `PRAGMA user_version`. Insert data, rebuild FTS (`INSERT INTO foods_fts(foods_fts) VALUES('rebuild')`), then `VACUUM` and `ANALYZE`.
6. **Metadata.** Write a `food_db_meta` table (build date, BLS version, OFF export date, row counts), shown in "Über die App".
7. **`--sample N`** flag builds a small dev database (~3,000 rows, mixed BLS/OFF) for fast iteration; the full database is only used for release builds (select via a Gradle property).
8. **Size budget.** Report sizes. If `foods.db` > 120 MB or the release APK > 90 MB, propose tighter filters (e.g. minimum scan count or completeness) and ask me.

**Schema** (adapt names to Kotlin conventions, keep semantics; all nutrients per 100 g or 100 ml):

```
foods(id INTEGER PK, source TEXT ['BLS'|'OFF'], source_id TEXT, barcode TEXT NULL (indexed),
      name TEXT, brand TEXT NULL, search_text TEXT,
      kcal REAL, protein REAL NULL, carbs REAL NULL, sugar REAL NULL,
      fat REAL NULL, fiber REAL NULL, salt REAL NULL,
      per_unit TEXT ['g'|'ml'], serving_g REAL NULL, serving_label TEXT NULL, popularity INTEGER)
foods_fts  FTS4 (content = foods: name, brand, search_text)
food_portions(food_id, label TEXT e.g. "1 Stück (mittel)", grams REAL, estimated INTEGER)
food_db_meta(key TEXT PK, value TEXT)
```

Treat 1 ml as 1 g for liquids (document this; show "ml" in the UI).

### 5.2 Text normalization and search

`normalize(s)`: lowercase → `ä`/`ae`→`a`, `ö`/`oe`→`o`, `ü`/`ue`→`u`, `ß`→`ss` → strip remaining diacritics → non-alphanumerics to spaces → collapse whitespace. Apply the identical function to stored text (Python) and queries (Kotlin). Both implementations are tested against the shared `normalize_cases.json`. Examples: "Käse", "Kaese", "kase" → `kase`; "Müsli" → `musli`; "Weißbrot" → `weissbrot`.

Search: tokenized prefix FTS query (`kase* gouda*`), fetch the top ~200, re-rank in Kotlin, show 50:

1. the user's custom foods and foods logged in the last 30 days (by frequency)
2. BLS foods whose name starts with the query
3. other BLS matches
4. OFF matches by popularity, then shorter names first

Debounce input by 150 ms. Target: results in < 150 ms on a mid-range device with the full database.

## 6. Calculations (in `:domain`, pure Kotlin, fully unit-tested)

### 6.1 BMR (Grundumsatz)
- **Mifflin-St Jeor** (default): `10 × kg + 6.25 × cm − 5 × age + 5` (männlich) / `− 161` (weiblich)
- **Katch-McArdle** (optional when body fat % is given): `370 + 21.6 × lean body mass (kg)`

### 6.2 TDEE (Gesamtumsatz) = BMR × activity factor

| Key | German label | Factor |
|---|---|---|
| SEDENTARY | Kaum aktiv – Bürojob, wenig Bewegung | 1.2 |
| LIGHT | Leicht aktiv – 1–3× Sport pro Woche | 1.375 |
| MODERATE | Mäßig aktiv – 3–5× Sport pro Woche | 1.55 |
| HIGH | Sehr aktiv – 6–7× Sport pro Woche | 1.725 |
| EXTREME | Extrem aktiv – körperliche Arbeit + Sport | 1.9 |

### 6.3 Goal → daily target
- **Abnehmen:** 0.25 / 0.5 / 0.75 / 1.0 kg per week; daily deficit = `rate × 7700 / 7`
- **Halten:** target = TDEE
- **Zunehmen:** 0.25 / 0.5 kg per week; surplus with the same formula
- Projected goal date = |current trend weight − goal weight| ÷ effective weekly rate, shown as "voraussichtlich am 12.03.2027"

### 6.4 Safety rules (implement exactly; always explain in friendly German, never block silently)
1. Users must be 18+ to set a weight goal; the formulas are not designed for minors.
2. The weekly loss rate is capped at 1 % of current body weight.
3. **Calorie floor:** the target never goes below 1,200 kcal (weiblich) / 1,500 kcal (männlich). If the chosen rate would go lower, clamp to the floor, recompute the effective rate and show it (e.g. "Mit deinem Profil sind etwa 0,62 kg pro Woche realistisch.").
4. If BMI < 18.5, "Abnehmen" is not offered (only Halten / Zunehmen). The goal weight must correspond to a BMI ≥ 18.5; validate the input.
5. Neutral tone, never shaming: being over the target is shown in a neutral/amber color with text like "120 kcal über dem Ziel", never alarm-red or guilt language.

### 6.5 Macros
- Default: Eiweiß 1.6 g per kg body weight, Fett 30 % of kcal, Kohlenhydrate = remainder (if negative, reduce fat to 20 % first). User can switch to a custom % split or g/kg values. 4 / 4 / 9 kcal per gram.

### 6.6 Weight trend
- Trendgewicht = exponential moving average with α = 0.1 over daily entries; gaps carry the trend forward (interpolate for the chart only).
- Weekly change and projections use the trend, not raw values.

### 6.7 Adaptive TDEE (Phase 7)
After ≥ 14 days with ≥ 10 logged days and ≥ 6 weight entries: `estimated TDEE = average daily intake − (Δ trend kg × 7700 / days)`. Show as a suggestion card ("Dein tatsächlicher Verbrauch liegt vermutlich bei ca. 2.350 kcal. Übernehmen?"). Never apply automatically.

### 6.8 Required test vectors
- Male, 30 y, 180 cm, 80 kg, MODERATE → BMR **1780**, TDEE **2759**; 0.5 kg/week → target **2209**
- Female, 30 y, 165 cm, 65 kg, LIGHT → BMR **1370.25**, TDEE **≈ 1884.1**; 0.75 kg/week → capped to 0.65 (1 % rule) → 1169 is below the floor → clamped to **1200**, effective rate **≈ 0.62 kg/week**
- kJ = kcal × 4.184. Compute in `Double`, display kcal as whole numbers, macros as whole grams in summaries and one decimal in detail views.

## 7. Screens and features (UI in German)

Open the food database in the background during onboarding (first-run asset copy) and show "Lebensmitteldatenbank wird vorbereitet …" if it is not ready yet.

### 7.2 Heute (diary)
- Date switcher (‹ Heute ›, tap for date picker, swipe between days)
- Ring: Ziel − Gegessen = Übrig (kcal); three macro progress bars
- Sections Frühstück / Mittagessen / Abendessen / Snacks with sums and a "+" button
- Entries show name, amount, kcal; tap to edit amount or meal; swipe to delete with a "Rückgängig" snackbar
- "Von gestern kopieren" per meal

### 7.3 Lebensmittel hinzufügen (search)
- Auto-focused search field, barcode button, chips: Zuletzt · Favoriten · Eigene
- Results: name, brand, kcal per 100 g/ml, source badge (BLS / OFF / Eigene)
- Actions: "Schnelleintrag" (kcal plus optional macros and a label), "Eigenes Lebensmittel anlegen"
- Logging a recently used food takes ≤ 3 taps

### 7.4 Portion & details
- Amount field with numeric keyboard; units: g/ml, "Portion (x g)" when known, `food_portions` entries ("1 Stück (mittel) ≈ 150 g", marked "ca." if estimated)
- Live preview of kcal and macros for the chosen amount
- Nährwerttabelle per 100 g/ml in German label style: Energie (kJ/kcal), Fett, Kohlenhydrate, davon Zucker, Ballaststoffe, Eiweiß, Salz
- Meal selector, favorite toggle, "Hinzufügen"

### 7.5 Barcode-Scanner
- CameraX preview, scan frame overlay, torch toggle, haptic feedback on a hit
- Formats: EAN-13, EAN-8, UPC-A, UPC-E (expand UPC-E to UPC-A; look up both 12- and 13-digit forms with a leading zero)
- Lookup order: `custom_food` → `foods.db`
- Not found → "Produkt nicht gefunden" → prefilled "Eigenes Lebensmittel anlegen" with the barcode, so the next scan finds it
- Codes starting with 20–29 are in-store / weighed-goods codes: show a hint that they cannot be in the database
- Manual barcode entry as fallback

### 7.6 Eigene Lebensmittel
Create, edit, delete; values per 100 g/ml as printed on the pack; optional portion size. Warn (don't block) if kcal and macros don't add up plausibly.

### 7.7 Gewicht
- Quick entry (defaults to today, one decimal, decimal comma)
- Chart: raw points + trend line + goal line; ranges 1M / 3M / 6M / 1J / Alles
- Stats: current trend weight, change over 7 and 30 days, remaining to goal, projected date
- Entry list with edit / delete

### 7.8 Statistik
- Week view: daily kcal bars vs. target line, average intake, total deficit/surplus and "≈ x kg" (÷ 7700)
- Month view with the same metrics; average macro split
- Days without entries are excluded from averages ("5 von 7 Tagen erfasst")

### 7.9 Profil & Einstellungen
- Edit profile and goal with live recalculation; macro targets; kcal/kJ; formula choice
- "Über die App": version, food DB metadata (sources, build date, row counts)
- "Alle Daten löschen" with confirmation
